# 工作流选择

Hub 整合两套 `mathmodel-skill` 项目的方法论，但不把它们混成第三套工作流。正确做法是根据团队的交付目标选择其中一套，再以另一套的检查思想作为参考。

## 快速结论

选择 **MathModel-Skill**，如果你：

- 使用推理能力和长上下文较强的模型。
- 需要完整的阶段编排和可恢复状态。
- 主要交付 Word，重视正式标题、公式和格式门禁。
- 希望证据通过后再集中完成正式写作。

选择 **MathModeling-skills**，如果你：

- 要求关键建模判断明确归属于人。
- 希望先做小规模风险探针，再投入完整实现。
- 特别担心结果过时、方法与实现错位或数字不可追溯。
- 希望用多名独立审计者阻止有缺陷的论文进入提交阶段。

## 核心差异

| 维度 | MathModel-Skill | MathModeling-skills |
| --- | --- | --- |
| 主要定位 | 正式竞赛交付流程 | 人在环的建模与审计流程 |
| 工作流表达 | S0–S8 阶段与可恢复状态 | 分阶段 Gate 与显式通过条件 |
| 模型路线 | 由流程形成并持续记录 | 主方案、基线、条件备选，经人工确认 |
| 风险控制 | preflight、workflow guard、证据与格式门禁 | 风险探针、结果冻结、三重最终审计 |
| 写作交付 | 正式 Word 为默认主流程 | 强调证据一致性，具体交付随配置变化 |
| 人的角色 | 审批阶段、判断结果与处理异常 | 明确拥有方法选择和解释权 |

## 不应怎样融合

- 不要把两套 orchestrator 同时设为入口。
- 不要混用它们的状态文件和输出目录。
- 不要从一套流程跨阶段调用另一套流程的内部 Skill。
- 不要因为名字相似就假设阶段可以一一对应。

可以借鉴的是原则。例如使用 MathModel-Skill 推进正式交付时，仍可采用“先基线、再风险探针”的思想；使用 MathModeling-skills 时，也可以借鉴正式 Word 的格式门禁。但这些补充检查必须由团队显式加入，不能冒充上游原生流程。
